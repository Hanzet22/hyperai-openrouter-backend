# Security 0.3 — Request Concurrency and Resource Protection

**Status:** Source implementation committed; runtime activation depends on the same Upstash Redis configuration required by Security 0.1.  
**Scope:** distributed in-flight request ceilings, upstream deadlines, disconnect cancellation, and bounded backpressure.

## What changed

1. **Distributed concurrency leases:** `lib/concurrency.js` uses atomic Redis Lua scripts and sorted-set leases. It applies a global ceiling and per-route ceilings across Vercel instances rather than relying on per-process memory.
2. **Bounded admission:** requests that exceed a ceiling receive HTTP 429 `CONCURRENCY_LIMITED` with `Retry-After: 5`. The system rejects excess work rather than building an unbounded in-memory queue.
3. **Crash recovery:** each permit expires after 70 seconds. A normal request releases its lease in `finally`; if an instance disappears, Redis expires the lease.
4. **Upstream deadlines:** chat 55 seconds, speech 50 seconds, and JSON endpoints 25 seconds. These are below the current Vercel function `maxDuration` values (60 seconds for chat/speech and 30 seconds for the JSON endpoints).
5. **Cancellation:** the shared guard listens for response closure and request abort/error events, passes an `AbortSignal` to upstream fetch, and clears its timeout/listeners after the operation.
6. **Backpressure:** chat streaming continues to wait for the response's `drain` event before writing more data. A disconnected client stops the stream and aborts upstream work.
7. **Fail-closed behavior:** missing or unavailable Redis returns HTTP 503 `CONCURRENCY_GUARD_UNAVAILABLE`. The guard never silently admits unbounded production traffic when its coordination store is down.

## Default concurrency ceilings

| Endpoint | Maximum in-flight upstream requests |
|---|---:|
| Chat | 8 |
| Decisions | 8 |
| Embeddings | 8 |
| Moderation | 8 |
| Rerank | 6 |
| Speech | 3 |
| **All routes combined** | **24** |

These are conservative initial limits, not capacity claims. Tune only after observing legitimate concurrency, provider response times, Redis latency, and Vercel usage. Shared NAT addresses are relevant to the separate IP rate limiter, but concurrency permits are shared service-wide rather than allocated per IP.

## Redis behavior

- Uses the existing `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` server-side environment variables.
- One atomic Lua operation prunes expired leases, checks both global and route counts, and creates the lease.
- A second atomic Lua operation removes the request's unique token from both sets.
- Redis server time is used for lease scores so different Vercel instances do not rely on their local wall clocks for lease expiry.
- The unique lease token prevents one request from releasing another request's permit.
- Redis command calls have a 2-second timeout. A failed acquire rejects the request; a failed release is recovered by the 70-second lease expiry.
- Each accepted upstream request adds two Redis operations in addition to the existing rate-limit operation. Monitor Upstash request usage and latency.

## Timeout policy

| Route group | Upstream deadline | Vercel function maxDuration |
|---|---:|---:|
| Chat streaming | 55 seconds | 60 seconds |
| Speech | 50 seconds | 60 seconds |
| Decisions, embeddings, moderation, rerank | 25 seconds | 30 seconds |

A deadline aborts the upstream fetch and returns HTTP 504 `UPSTREAM_TIMEOUT` when a response can still be sent. A client disconnect cancels upstream work without attempting to write another response. Vercel may still terminate an invocation at its platform-level maximum duration; application deadlines are intentionally shorter so cleanup has time to run.

The chat stream's existing `writeWithBackpressure` helper waits for `drain` when the response buffer is full. This prevents the application from continuously writing into a slow client, but does not create a durable stream or queue.

## Why there is no in-memory queue

Vercel Functions scale across instances and can process multiple concurrent invocations within a shared instance. A module-level counter or queue would only observe one instance and would not enforce a deployment-wide limit. Redis coordinates the admission decision across instances. The current design rejects excess requests with 429 rather than retaining request bodies and upstream work in a queue.

## Operational requirements

1. Configure both Upstash variables in Vercel Production and Preview.
2. Redeploy after adding or changing the variables.
3. Confirm the existing Security 0.1 rate limiter succeeds first; both guards use the same Redis service.
4. Verify a normal request reaches the upstream provider.
5. In a controlled test environment, issue requests concurrently and confirm requests above the configured ceiling receive 429.
6. Verify that disconnecting a chat stream cancels the upstream request and releases the permit.
7. Verify that a stalled upstream request is aborted at the configured deadline and returns 504 when the client is still connected.
8. Monitor Upstash command usage, Redis errors, Vercel function duration, 429/503/504 rates, and OpenRouter usage.

Do not run uncontrolled concurrency or load tests against production or a paid provider. Use mocked upstreams or a bounded, owner-authorized staging test.

## Limitations and residual risks

- This is a concurrency ceiling, not authentication, per-user fairness, or a daily monetary spend cap.
- The global ceiling is shared by all users. A single source of traffic can occupy available slots; authentication and identity-aware quotas remain separate future work.
- Lease expiry is a crash-recovery mechanism. The 70-second TTL exceeds the current application deadlines; if future route deadlines exceed the lease duration, add safe lease renewal before increasing those deadlines.
- If a function is forcibly terminated, it cannot run its release script; the lease expires automatically.
- If Redis is unavailable, AI traffic fails closed. This improves protection but reduces availability until Redis is restored.
- Client cancellation depends on the hosting runtime delivering request/response lifecycle events. Vercel documents request cancellation handling per route; verify behavior in the deployed runtime.
- No production concurrency/load test, real provider timeout test, or production Upstash activation was performed as part of this source change.

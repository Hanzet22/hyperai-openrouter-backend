# Security 0.7 — Application Security Hardening

Status: implementation review and regression baseline recorded. This document does not claim a penetration test or production security certification.

## Scope reviewed

- Six API handlers: chat, decisions, embeddings, moderation, rerank, and speech.
- Shared request handling in `lib/openrouter.js`.
- Browser rendering in `public/index.html`.
- Existing Node test suite and dependency/workflow inventory.

## Findings and disposition

| Area | Review result | 0.7 disposition |
|---|---|---|
| Request validation | All six routes validate their core fields; chat has model and message allowlists, and shared body size is capped at 256 KiB. Several route-specific object schemas intentionally preserve provider payload compatibility. | Preserve existing contracts; pin validation behavior with regression tests. |
| Markdown/XSS | The custom renderer now builds message content with DOM nodes and text nodes; untrusted message text is assigned through `textContent`. Auto-links are parsed as URLs, limited to HTTP(S), reject embedded credentials, and use `rel="noopener noreferrer"`. Dynamic message rendering no longer assigns `innerHTML`. | Keep the renderer dependency-free; source-level regression tests pin safe DOM sinks and URL policy. Real-browser testing is still required to validate behavior across browsers. |
| SSRF | User-controlled URLs are not accepted by any of the six public API routes. Upstream destinations are fixed in server code. Redis REST URLs are deployment configuration, not request input. | No URL-fetch feature or user-controlled upstream target was found. SSRF risk is currently not applicable to these routes; re-review if URL fetching, webhooks, imports, or arbitrary proxying are added. |
| Error disclosure | Upstream error text is bounded but can still be provider-originated. JSON encoding prevents it from becoming markup in the API response, while the frontend escapes rendered content. | Keep errors bounded; do not log request bodies, credentials, or raw client IPs. Provider messages are not guaranteed to be free of internal details. |
| Resource limits | Shared JSON body cap and per-route text/count limits exist. Speech buffers the upstream audio response with an enforced 8 MiB ceiling; both declared content-length and streamed over-limit responses are rejected by regression tests. | The audio body remains buffered in memory up to the cap; streaming directly to the client is a future optimization. |
| Dependencies | Runtime package manifest currently declares no npm dependencies. | Avoid adding a sanitizer/parser dependency without a demonstrated need and compatibility review. Continue Dependabot and pinned workflow actions. |

## Security invariants

1. Client input must never select an arbitrary upstream URL.
2. Model selection remains server-allowlisted.
3. Client-supplied roles remain restricted to user/assistant.
4. Untrusted message content is rendered with DOM creation APIs and text nodes, never HTML string sinks.
5. Auto-linked URLs remain HTTP(S)-only, reject embedded credentials, and open with `noopener noreferrer`.
6. Tests must pin these invariants so a future refactor cannot silently weaken them.

## Verification limits

- Node unit tests do not replace real-browser DOM/XSS testing.
- No penetration test, external security assessment, load test, or provider-outage test is claimed.
- Redis-backed rate limiting/concurrency/resilience still require the separate 0.6 activation and runtime verification.
- The current frontend uses a custom lightweight Markdown renderer, not a full Markdown implementation or a maintained HTML sanitizer.
- Source-level DOM sink tests are not a substitute for browser automation or a dedicated XSS assessment.

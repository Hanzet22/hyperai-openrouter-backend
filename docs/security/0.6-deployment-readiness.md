## Goal

Verify the deployed HyperAI service and its Redis dependency without sending prompts, generating model output, or creating paid upstream usage.

## Deployment readiness checker

The repository includes `scripts/verify-deployment.mjs`. It performs only:

1. HTTPS GET of the configured homepage.
2. Checks for the configured baseline response headers:
   - `X-Content-Type-Options: nosniff`
   - `X-Frame-Options: DENY`
   - `Referrer-Policy: strict-origin-when-cross-origin`
   - HSTS with `max-age=31536000`
   - Presence of `Permissions-Policy`
3. OPTIONS preflight against all six API routes and checks for HTTP 204 and `X-Request-Id`.
4. Authenticated Upstash REST `PING`; it expects `PONG`.

The checker does not send POST requests, prompts, audio, model payloads, or perform stress/load tests. It never prints Redis credentials.

### Run

Use a trusted local shell or CI secret store. Do not paste secrets into chat, GitHub issues, logs, or source code.

```sh
HYPERAI_BASE_URL="https://your-production-domain" \
UPSTASH_REDIS_REST_URL="https://your-database.upstash.io" \
UPSTASH_REDIS_REST_TOKEN="your-token" \
npm run verify:deployment
```

Optional CORS check for a known, authorized frontend origin:

```sh
HYPERAI_TEST_ORIGIN="https://your-frontend-domain"
```

When supplied, the checker sends that Origin on preflight and verifies the exact `Access-Control-Allow-Origin` response.

## Required Vercel configuration

The project requires both variables in **Production and Preview**:

- `UPSTASH_REDIS_REST_URL`
- `UPSTASH_REDIS_REST_TOKEN`

Set the REST URL as an encrypted value and the REST token as a sensitive/secret value in the Vercel project environment settings. Do not add them to GitHub repository files or commit history.

The database must be provisioned in an Upstash account controlled by the project owner. Choose a Redis-compatible database with REST API access enabled. Copy the REST URL and REST token directly into Vercel's secure environment-variable form. Never place the token in a public issue, source file, browser client, or chat.

After adding both variables:
1. Confirm both Production and Preview targets are selected.
2. Redeploy the latest `main` commit.
3. Run the readiness checker against the Production URL and a Preview URL separately.
4. Verify that all six API routes pass OPTIONS preflight.
5. Review Vercel runtime logs for `hyperai.request.completed` events and absence of `*.unavailable` / `resilience.store_error` events.

## Safe runtime verification

The checker validates Redis connectivity with PING only. It does not prove the Lua scripts, rate-limit counters, concurrency leases, or circuit-breaker state transitions work against the live database.

Those behaviors are covered by mocked automated tests. A real integration test should be performed in a dedicated Preview deployment with an authorized test key and a controlled test window. Do not run a load test or paid AI generation against Production as part of routine readiness verification.

## Deployment and hosting constraints

- A Vercel deployment in READY state confirms that the build/deployment completed; it does not prove that Redis is configured or that protected API POST requests can execute.
- The production guards intentionally fail closed when Redis is absent or unavailable.
- Vercel Hobby runtime-log retention is limited; an empty recent log query is not proof of application health.
- CORS is not authentication. API endpoints remain callable by clients outside the intended browser UI unless application-level authentication is added.
- No external alerting, durable metrics store, p95/p99 aggregation, or production load test is included in this phase.

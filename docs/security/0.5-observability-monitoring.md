# Security 0.5 — Observability & Operational Monitoring

## Scope

Security 0.5 adds structured, privacy-conscious operational telemetry to the six API routes and the existing rate-limit, concurrency, upstream resilience, and usage controls.

Telemetry is emitted to the Vercel Function runtime logs through `console.info`. This phase does not add a database, analytics SDK, metrics endpoint, or paid monitoring dependency.

## Events

| Event | Meaning |
|---|---|
| `hyperai.request.completed` | API response completed; includes route, method, status, duration, environment, and generated request ID. |
| `hyperai.request.aborted` | Client disconnected before the response completed. |
| `hyperai.openrouter.usage` | Provider usage metadata when available: model, route, generation ID, token counts, and reported cost. |
| `hyperai.rate_limit.rejected` | Rate limit returned HTTP 429. |
| `hyperai.rate_limit.unavailable` | Rate-limit protection could not run; includes a bounded reason code. |
| `hyperai.concurrency.rejected` | Distributed concurrency ceiling returned HTTP 429. |
| `hyperai.concurrency.unavailable` | Concurrency guard could not run. |
| `hyperai.resilience.circuit_open` | Provider/model circuit rejected a request during cooldown. |
| `hyperai.resilience.half_open_probe` | A single recovery probe was admitted. |
| `hyperai.resilience.outcome` | Upstream outcome recorded by the circuit breaker. |
| `hyperai.resilience.store_error` | Circuit state could not be persisted to Redis. |

Every event is a single JSON object with an ISO-8601 timestamp. Request IDs are generated server-side and returned as `X-Request-Id`.

## Privacy and redaction

The telemetry helper uses an explicit field allowlist. It does not accept arbitrary request objects or serialize request/response bodies.

Never add any of the following to telemetry:
- Prompts, user messages, model output, uploaded content, or speech input/audio.
- API keys, Redis tokens, authorization headers, cookies, or environment variable values.
- Raw client IP addresses or other direct identifiers.
- Full upstream error bodies or arbitrary exception messages.

Model IDs and provider generation IDs may be present in usage events. Treat runtime logs as operational data: restrict dashboard access to project operators and apply the retention controls available in the hosting account.

## Operational review

Review Vercel Runtime Logs for:
- Increasing `hyperai.request.aborted` counts or elevated request duration.
- Repeated 429 events, which may indicate abuse or limits that are too restrictive.
- Any `*.unavailable` or `resilience.store_error` events, which indicate protection dependencies are not healthy.
- Repeated circuit-open events for the same provider/model.
- Unexpected usage or reported-cost patterns.

Suggested initial investigation thresholds (not automated alerts):
- Investigate a sustained 5xx rate above 5% over 5 minutes.
- Investigate repeated Redis/protection-unavailable events immediately.
- Review a sudden 3x increase in request volume or provider-reported cost against the normal baseline.
- Investigate sustained p95 latency above the expected provider and function budget.

These are operator starting points, not measured HyperAI baselines. Configure actual alerting only after observing normal traffic and selecting a supported monitoring integration.

## Limitations

- Runtime logs are not a durable metrics database and do not provide reliable pre-aggregated counters or histograms.
- No dashboard, alert delivery, log export, or retention policy is configured by this code change.
- Request duration is measured at the API response lifecycle; it is not a complete provider-only latency breakdown.
- Usage events depend on usage metadata returned by the upstream provider.
- Tests use mocked Redis/provider responses; they do not establish production availability or performance.

## Verification

Run:

```sh
npm test
```

The observability tests verify structured JSON output, request lifecycle events, and exclusion of prompt, authorization, and IP fields. Existing rate-limit, concurrency, and resilience suites continue to exercise their respective behavior.

## Activation requirements

Security 0.1, 0.3, and 0.4 require both `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` in Vercel Production and Preview environments. Configure them through the project owner's secure Vercel/Upstash dashboards, then redeploy and verify runtime behavior. Never paste secrets into chat, issues, logs, or source control.

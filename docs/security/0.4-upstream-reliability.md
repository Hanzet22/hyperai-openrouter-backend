# Security 0.4 — Upstream Reliability and Failure Resilience

**Status:** Source implementation committed; runtime activation depends on the existing Upstash Redis REST configuration used by Security 0.1 and 0.3.  
**Scope:** Provider/model-scoped circuit breaking, bounded rate-limit retry, failure classification, cooldown, and recovery probing.

## What changed

1. Added `lib/resilience.js` with a distributed circuit breaker coordinated by Upstash Redis Lua scripts.
2. Circuit keys are SHA-256 hashes of the provider/model key; raw model identifiers are not embedded in Redis keys.
3. The breaker uses `CLOSED`, `OPEN`, and `HALF_OPEN` behavior:
   - **CLOSED:** requests are admitted and transient failures are counted.
   - **OPEN:** requests fail fast with HTTP 503 `UPSTREAM_CIRCUIT_OPEN`.
   - **HALF_OPEN:** after the cooldown, one probe lease is admitted; concurrent probes are rejected.
4. Five transient failures within a 30-second rolling counter open the circuit for 30 seconds. The first request after cooldown receives the probe lease. A successful upstream response clears the breaker; a transient failure reopens it.
5. The Redis server clock is used to calculate cooldown expiry. The half-open probe lease expires after 10 seconds if the function disappears.
6. The existing Upstash Redis REST variables are reused. Production and Preview fail closed if the resilience store is missing or unavailable; local development bypasses distributed coordination.

## Failure classification

| Outcome | Circuit treatment | Automatic retry |
|---|---|---|
| HTTP 2xx | Success; reset failure state | No |
| HTTP 429 | Transient failure | At most one retry, only when a valid `Retry-After` fits within the 1-second retry ceiling |
| HTTP 500, 502, 503, 504 | Transient failure | No |
| Network/fetch exception | Transient failure | No; outcome may be ambiguous for POST operations |
| Other HTTP 4xx | Neutral; does not count as provider failure | No |
| Circuit-store failure | Fail closed with HTTP 503 | No |

The retry policy deliberately does **not** replay arbitrary POST requests after network errors or 5xx responses. A provider may have accepted and processed a generation before the connection failed; blindly replaying it could duplicate work and charges. HTTP 429 is the only retry candidate, and only one retry is allowed when the provider supplies a valid `Retry-After` value no greater than one second. Delta-seconds and HTTP-date forms are parsed. Invalid or longer values are surfaced to the caller rather than slept through.

The retry applies only before the response body is consumed. For chat, this is before SSE headers and stream output are sent. Once streaming begins, the stream is never restarted automatically.

## Integration

- JSON endpoints use the shared `forwardJson` wrapper and key the circuit by the selected model.
- Chat uses the selected model key and permits the bounded pre-stream 429 retry.
- Speech uses the speech model key and circuit breaker but does not retry generation requests.
- The circuit breaker is independent per model key; a failing model does not automatically open circuits for unrelated models.
- The existing concurrency guard still owns upstream deadlines and client-disconnect cancellation.

## Redis operations and limits

A normal production request adds a circuit check and a final outcome write to the existing rate-limit and concurrency Redis operations. Half-open coordination uses a short-lived probe key. Monitor Upstash command usage and latency.

This implementation is a conservative first resilience layer, not a full provider health monitor. It does not perform background health checks, automatic model fallback, or retry ambiguous POST failures. Circuit state is shared across Vercel instances. A race between concurrent successes and failures can influence the simple failure counter; tune thresholds only after observing real traffic.

## Verification checklist

- [ ] CI passes all tests on the commit containing this phase.
- [ ] Configure both Upstash variables in Vercel Production and Preview.
- [ ] Redeploy and confirm normal requests pass through the Redis-backed guards.
- [ ] In a mocked or owner-authorized staging environment, simulate five transient failures for one model and confirm the circuit opens.
- [ ] Confirm a different model remains available while the first model's circuit is open.
- [ ] Confirm one half-open probe is admitted after cooldown.
- [ ] Confirm a 429 with short valid `Retry-After` gets at most one retry.
- [ ] Confirm invalid/missing/long `Retry-After` is not retried.
- [ ] Confirm 5xx and network exceptions do not trigger POST replay.
- [ ] Confirm chat stream output is never replayed after SSE begins.
- [ ] Review Upstash operation usage, Vercel duration/error metrics, and OpenRouter usage.

Do not run uncontrolled load or failure tests against production or a paid provider. Use mocks or a bounded, owner-authorized staging environment.

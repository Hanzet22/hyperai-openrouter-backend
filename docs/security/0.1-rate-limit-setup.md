# Security 0.1 — API Rate Limiting Setup

**Implementation:** source code is present in `main`.  
**Activation:** production traffic remains blocked with HTTP 503 until both Upstash variables are configured in Vercel and the deployment is redeployed.

## What this phase does

- Applies a shared, atomic Redis-backed limiter to all six POST API routes.
- Uses Vercel's `x-real-ip` request header as the client IP source.
- Hashes the IP before placing it in a Redis key; the raw IP is not included in the key.
- Enforces per-route limits and one global request ceiling in a rolling-by-fixed-window 60-second bucket.
- Returns HTTP 429 with `Retry-After` when a quota is reached.
- Fails closed with HTTP 503 if Redis is missing, unavailable, misconfigured, or the trusted client IP is unavailable.
- Does not log prompts, API keys, Redis tokens, or raw IP addresses.

## Default limits

| Endpoint | Per IP / 60 seconds |
|---|---:|
| `POST /api/chat` | 8 |
| `POST /api/decisions` | 12 |
| `POST /api/embeddings` | 20 |
| `POST /api/moderate` | 20 |
| `POST /api/rerank` | 10 |
| `POST /api/speech` | 4 |
| All endpoints combined | 120 globally / 60 seconds |

These are conservative starting limits, not provider cost guarantees. IP-based limits can affect multiple people sharing one public IP (school, campus, office, mobile carrier NAT). Review real traffic and adjust only with evidence.

## Configure Upstash

1. Create a Redis database in the Upstash console.
2. Open its REST API details and copy the REST URL and REST token.
3. In Vercel, open **Project → Settings → Environment Variables**.
4. Add these variables to every environment that should serve production-like API traffic:

   - `UPSTASH_REDIS_REST_URL`
   - `UPSTASH_REDIS_REST_TOKEN`

5. Keep both values server-side. Never add them to `public/index.html`, frontend JavaScript, public issues, or committed environment files.
6. Redeploy the project.
7. Test a normal request, then repeat requests until the applicable limit is reached. Confirm that the response becomes HTTP 429 and includes `Retry-After`, `RateLimit-Limit`, `RateLimit-Remaining`, and `RateLimit-Reset`.

If either variable is absent in production, the API returns HTTP 503 by design. This prevents accidental unmetered use. Local non-production development bypasses the Redis limiter; do not use that bypass as evidence of production protection.

## Trust boundary

Vercel documents `x-real-ip` as the client IP header supplied to Functions. The implementation intentionally does not fall back to arbitrary client-controlled forwarding headers. If the app is later placed behind another proxy, review the proxy trust chain before changing this behavior.

## What this does not provide

- It is **not authentication** and does not identify a person or account.
- It does not create per-user quotas, paid tiers, account bans, or tenant isolation.
- Distributed clients can still spread requests across different IP addresses.
- It is not a guaranteed daily spending cap for OpenRouter.
- It does not replace provider usage limits, budget alerts, WAF/firewall rules, or incident monitoring.
- It does not protect static files or unrelated Vercel endpoints.

The current frontend is designed for anonymous browser use. A secret API token embedded in browser JavaScript would be public and is not an acceptable authentication design. A private/API-client mode requires a separate server-verifiable identity or credential design.

## Operational checks

- Keep OpenRouter's own usage limits/budget alerts enabled where available.
- Keep OpenRouter Web Search disabled unless intentionally reviewed and enabled.
- Monitor Vercel Function invocations and Upstash usage.
- If Redis is unavailable, restore Redis configuration/service before reopening API traffic; do not change the code to silently fail open.
- Review limits after observing legitimate traffic, especially for users sharing NAT addresses.
- Do not run load tests against production without explicit provider/hosting authorization and a bounded test plan.
